# Архитектура самостоятельной студии

Документ описывает границы самостоятельной версии на Next.js 16 и Node.js 24, сохранённую логику производства фильма и контракты адаптеров. Приложение рассчитано на одного владельца и один сервер с постоянным локальным хранилищем. Исходный код не включает фильмы владельца, медиатеку и ключи провайдеров.

## 1. Компоненты и поток данных

```text
Браузер
  app/studio.tsx: карточки, выбор, утверждение, окна серий
  React Query: снимок открытого проекта и обновление интерфейса
  таймер очереди: POST существующей задачи примерно раз в 5 секунд
  FFmpeg WASM: аниматик, монтаж, подготовка файлов sync
          |
          | приватные HTTP API и потоковая выдача медиа
          v
Next.js / Node.js
  авторизация владельца и проверка запросов
  app/api: валидация команд, проверки владельца, работа с ревизиями
  lib/*: сценарий, зависимости, утверждения, речь, планы, бюджет
  adapters: SQLite + приватные объекты и multipart на диске
          |
          | исходящий HTTPS, пользовательские ключи
          v
API моделей: генерация, получение статуса и загрузка результата
```

Браузер не обращается к платным API напрямую и не получает расшифрованные ключи. Он отправляет проверенную пользователем серию серверу. Сервер сохраняет задачи до их исполнения, а затем обрабатывает существующую задачу по отдельному запросу клиента.

## 3. Авторизация и секреты

Самостоятельная версия использует пароль одного владельца и собственную сессию. `ADMIN_USERNAME` задаёт имя входа, `ADMIN_PASSWORD_HASH` — scrypt-хэш в формате `scrypt:32768:8:1:<base64url salt>:<base64url digest>`. Соль содержит 16 байт, результат — 64 байта. Разделители-двоеточия исключают раскрытие `$` при загрузке переменных окружения.

`SESSION_SECRET` содержит не менее 32 UTF-8 байт и защищает подписанную сессию. Cookie `kadr_session` действует 12 часов, имеет HttpOnly и SameSite=Strict; на HTTPS добавляется Secure. В подписи учитываются имя и хэш пароля, поэтому изменение этих параметров также делает прежние сессии недействительными. Отдельный `VAULT_KEY` — 32 случайных байта в base64 — служит ключом AES-GCM для API-ключей провайдеров. Эти секреты имеют разные назначения.

Стабильный идентификатор владельца — строка `owner`. Он не меняется при смене имени входа и используется в SQL-условиях доступа и при шифровании. Даже при одном владельце сохраняются проверки принадлежности проекта, asset и upload-session. Клиент не назначает owner произвольным заголовком. `app/auth.ts` проверяет вход серверной страницы и перенаправляет на `/login`, когда сессия отсутствует.

Обёртка `owner(req, write)` вызывается маршрутами перед чтением или записью. Для записей проверяется точное совпадение Origin с `APP_ORIGIN`. Значение содержит только origin без пути и завершающего слеша: HTTPS для внешнего адреса либо HTTP для localhost/loopback. Неполная или некорректная конфигурация не открывает доступ без пароля. Статические файлы движка FFmpeg публичны, пользовательские медиа — только через авторизованный API.

Ключ провайдера шифруется случайным 12-байтовым IV и AES-GCM. Дополнительные аутентифицируемые данные — строка `owner:provider`. В БД хранится JSON с IV и шифротекстом. API подключений возвращает наличие ключа и время изменения, но не расшифрованное значение.

Потеря `VAULT_KEY` делает существующие шифротексты непригодными для чтения. Смена owner также меняет AAD. Миграция или ротация требуют отдельной процедуры, а не изменения одного поля конфигурации.

## 4. Состояние проекта

Основные сущности определены в `lib/domain.ts`:

- `Project`: конфигурация, ревизия, карточки, задачи, расходы, сравнения голосов, аниматики и история удаления.
- `Item`: карточка этапа, её варианты, `selectedId`, `approvedId`, связь с планом сценария.
- `Variant`: текст или файл, модель, монтажные параметры, речь, референсы и снимок зависимостей `deps`.
- `Job`: одна попытка генерации с `batchId`, моделью, промптом, входами, статусом, квитанцией провайдера и денежными полями.

Выбор и утверждение независимы. Генерация добавляет новый вариант; она не присваивает ему утверждение. Ручное сохранение создаёт новую версию. Повторное подтверждение стиля, голоса или видео — отдельная явная операция, которая допускается после проверки актуальной основы и сохраняет тот же материал.

`dependencies(project, stage)` сериализует версию конфигурации и IDs утверждённых вариантов участвующих предыдущих карточек. `isApproved` проверяет совпадение этого снимка и готовность предшествующих этапов. Удалённые и архивные карточки исключаются через `participates`.

### Этапы и аниматик

Сохраняемые номера этапов остаются 0–8: общий сценарий, герои, стиль, образы/локации, подробный сценарий, раскадровка, голоса, видеопланы, финал. UI показывает отдельный аниматик между голосами и видео с ID 9. Его варианты находятся в `Project.animatic`, а не подменяют аудио в карточке этапа 6.

Завершённость голосов требует утверждённых актуальных аудиофайлов и совпадения выбранного варианта с утверждённым. В режиме `plans` прежняя общая дорожка не участвует; в режиме `track` не участвуют записи отдельных планов. Для фильма без речи предусмотрен отдельный путь проверки.

Аниматик хранит `animaticBasis`: подпись использованных кадров, выбранного аудио, порядка, длительностей, trim, offset, volume и речевых метаданных. Проверка не обновляет эту подпись автоматически. Изменившиеся источники требуют нового файла просмотра. Утверждение аниматика требует утверждения выбранных голосов; оно не изменяет их утверждения.

Обычная готовность видеогенерации определяется предшествующими сохраняемыми этапами и не добавляет проверку `Project.animatic`. Это существующее разделение технических ограничений и отдельного просмотра.

## 5. SQLite и контракт DB

SQLite хранится в `DATA_DIR/studio.sqlite`, приватные файлы — в `DATA_DIR/private-files`. Значение DATA_DIR по умолчанию — `./data`, разрешаемое относительно рабочего каталога процесса. База и объекты не должны размещаться в `public`, временном каталоге сборки или одноразовом слое контейнера.

`LocalDatabase` использует `node:sqlite` (`DatabaseSync`), WAL, foreign keys и `busy_timeout=5000`. Соединение открывается с уже подготовленной схемой. `scripts/migrate.mjs` применяет явные миграции перед запуском; обычный запрос приложения не создаёт таблицы. `scripts/setup.mjs` подготавливает `.env` и случайный пароль, `scripts/start.mjs` запускает приложение или dev-режим. Docker entrypoint выполняет миграции и запускает standalone server. Подробные команды установки описываются отдельно.

| Таблица | Содержимое |
| --- | --- |
| `projects` | `id`, `owner`, `title`, `state`, `revision`, `updated`. |
| `assets` | Приватная медиатека: ID объекта, владелец, имя, MIME, размер, дата. |
| `credentials` | Зашифрованные ключи по паре owner/provider. |
| `asset_uploads` | Незавершённая загрузка: ID, владелец, ожидаемый размер, MIME и upload ID. |

Денежная история, задачи и варианты находятся внутри состояния проекта, а не в отдельных SQL-таблицах. Схема описана в `db/schema.ts`; изменения таблиц должны оформляться воспроизводимо.

Интерфейс DB из `lib/storage-types.ts`:

```ts
type SqlValue = string | number | bigint | null | Uint8Array;
interface QueryResult<T = Record<string, unknown>> {
  results: T[];
  success: true;
  meta: { changes: number };
}
interface PreparedStatement {
  bind(...values: SqlValue[]): PreparedStatement;
  first<T>(): Promise<T | null>;
  all<T>(): Promise<QueryResult<T>>;
  run(): Promise<QueryResult>;
}

interface Database {
  prepare(sql: string): PreparedStatement;
  batch(statements: PreparedStatement[]): Promise<QueryResult[]>;
}
```

Используются параметры `?`, `INSERT OR IGNORE`, `ON CONFLICT ... DO UPDATE`, SELECT/UPDATE/DELETE. `batch` должен выполнять всю группу в одной транзакции: завершение загрузки одновременно регистрирует asset и удаляет upload-session. `run().meta.changes` должно быть реальным числом изменённых строк.

### Конкурентная запись

`saveProject` сначала проверяет владельца и ожидаемую ревизию. Затем сохраняет новый снимок и выполняет UPDATE с условиями `id`, `owner`, `revision`. Если строка уже изменена другим запросом, возвращается конфликт 409. Ревизия увеличивается только после успешной записи.

`mutate` может заново прочитать проект и повторить чистое изменение до пяти раз при конфликте ревизии. Поэтому внутрь переданной ему функции нельзя помещать платный запрос провайдеру или другой необратимый внешний эффект: функция может исполниться повторно.

`batch` выполняется через `BEGIN IMMEDIATE`, синхронные операции без `await` между ними и COMMIT/ROLLBACK. Это не позволяет другому запросу процесса вклинить SQL внутрь транзакции. Проверка CAS остаётся обязательной даже при одном владельце: два окна и фоновая проверка задачи создают конкурентные запросы.

## 6. Приватные объекты и большие snapshots

`FileObjectStore` обслуживает медиатеку и служебные snapshots проекта. Пользовательские имена файлов — метаданные. Логические ключи не используются как пути: адаптер вычисляет SHA-256 ключа и размещает объект в `DATA_DIR/private-files/objects/<hash>/`. Внутри находятся неизменяемые файлы данных и атомарно обновляемый `object.json`. Сессии располагаются в `DATA_DIR/private-files/uploads/<uploadId>/`, upload ID проверяется как UUID.

Публикация выполняется после полной записи и fsync данных, затем атомарной замены JSON-указателя. Читатель, уже получивший прежний указатель, может дочитать прежний файл. Метаданные содержат размер и hash/etag, а чтение проверяет соответствие фактического размера. В одном Node-процессе операции с объектами и multipart защищены общими блокировками по ключу. Это блокировки памяти процесса, а не распределённые блокировки между серверами.

Для небольшого проекта `projects.state` содержит JSON целиком. При размере больше 512 000 UTF-8 байт `project-state.ts` сохраняет неизменяемый JSON-объект, а SQL-строка содержит небольшой указатель:

```text
$kadrProjectState: "r2-v1"
key: project-state/<sha256([owner, projectId])>/<revision>/<uuid>.json
size: число байтов
sha256: контрольная сумма содержимого
revision: ревизия проекта
```

Название `r2-v1` — метка совместимого формата, а не требование использовать облачный R2. В самостоятельной версии этот логический ключ обслуживает приватный дисковый адаптер; строка со слешами не превращается в произвольный путь на диске.

При чтении проверяются область owner/project, ревизия, размер, SHA-256, UTF-8 и базовая структура проекта. Отсутствующий или повреждённый snapshot не заменяется пустым проектом. При записи новый объект создаётся **до** CAS в SQL. Старые объекты и объект при неоднозначном исходе записи не удаляются автоматически: сохранённый указатель или параллельный читатель могут ещё ссылаться на них.

У snapshot нет записи в `assets`; он не появляется в медиатеке и не выдаётся через `/api/assets/:id`.

Основные методы объектного контракта; полные типы метаданных находятся в `lib/storage-types.ts`:

```ts
type ObjectInput = ArrayBuffer | Uint8Array | string | ReadableStream<Uint8Array>;
type ObjectOptions = { httpMetadata?: { contentType?: string } };
type StoredObject = {
  key: string;
  size: number;
  etag: string;
  uploaded: Date;
  httpMetadata: { contentType?: string };
};
type StoredObjectBody = StoredObject & {
  body: ReadableStream<Uint8Array>;
  arrayBuffer(): Promise<ArrayBuffer>;
  range?: { offset: number; length: number };
};
type UploadedPart = { partNumber: number; etag: string };
interface MultipartUpload {
  key: string;
  uploadId: string;
  uploadPart(partNumber: number, value: ObjectInput): Promise<UploadedPart>;
  complete(parts: UploadedPart[]): Promise<StoredObject>;
  abort(): Promise<void>;
}
interface ObjectStore {
  put(key: string, value: ObjectInput, options?: ObjectOptions): Promise<StoredObject>;
  get(key: string, options?: { range?: Headers }): Promise<StoredObjectBody | null>;
  head(key: string): Promise<StoredObject | null>;
  createMultipartUpload(key: string, options?: ObjectOptions): Promise<MultipartUpload>;
  resumeMultipartUpload(key: string, uploadId: string): MultipartUpload;
}
```

`size` в частичном GET означает полный размер файла. `range` описывает возвращаемый участок; HTTP-маршрут использует эти значения для Content-Range и Content-Length. Дисковый адаптер читает поток блоками до 64 КиБ и поддерживает `bytes=start-end`, `bytes=start-` и `bytes=-suffix`. Некорректный или недоступный диапазон возвращает ошибку 416 с `Content-Range: bytes */<size>`. Несколько диапазонов одним запросом не поддерживаются.

Приложение не требует публичных URL, подписанных ссылок или обхода всех объектов. Выдача media сначала проверяет запись `assets` и owner, затем читает объект. Заголовки ответа: приватное кэширование, Accept-Ranges и запрет MIME-sniffing.

## 7. Загрузка файлов частями

`lib/asset-upload.ts` выбирает протокол:

- до 8 МиБ — обычный multipart/form-data POST `/api/assets`;
- больше 8 МиБ и до 1 ГиБ — сессия `/api/assets/uploads`, последовательные части по 8 МиБ, затем завершение.

Прямой endpoint и `storeAsset` ограничены 50 МиБ; этот же предел действует для скачивания результата провайдера. Большой пользовательский upload не увеличивает лимиты API-референсов или sync.

Для сессии сохраняются ожидаемые размер, MIME и owner. Каждый PUT проверяет номер и точное число байтов части, включая последнее неполное окно. Чтение тела ограничено ожидаемым размером даже без Content-Length.

`uploadPart(number, bytes)` возвращает номер и etag. Повторная отправка того же номера безопасно заменяет часть. `complete(parts)` должен проверить перечень частей и атомарно опубликовать полный файл, не собирая 1 ГиБ в общий Buffer. Возвращаемый размер сверяется с ожидаемым.

Если файл завершён, но SQL-запись или ответ потерялись, повторный POST проверяет `head` и завершает регистрацию без новой загрузки. DELETE незавершённой сессии не удаляет уже готовый файл: обнаруженный объект регистрируется. Очистка старых сессий запускается ограниченно при создании новой загрузки, а не отдельным планировщиком.

Обычный клиент повторяет PUT части и завершение до трёх раз. Сессии и части должны переживать разные HTTP-запросы и перезапуск процесса. Незавершённые части другого хранилища не переносятся автоматически.

## 8. API и исполнение платных задач

| Группа маршрутов | Назначение |
| --- | --- |
| `/api/projects`, `/api/projects/:id` | Создание, чтение и команды изменения проекта. |
| `/generate` | Обычная серия текстовых, графических, аудио- или видеовариантов. |
| `/generate-storyboard` | По одному изображению на выбранный план. |
| `/generate-speech`, `/generate-voice-tests` | Реплики по планам и сравнения голосов. |
| `/generate-remaining` | Обычное видео одной модели для планов без готового ролика. |
| `/generate-lipsync` | Очередь обработки выбранных изображений/видео и речи. |
| `/jobs/:jobId` | Отправка сохранённой задачи, опрос провайдера, сохранение результата и точечное восстановление. |
| `/api/assets`, `/api/assets/:id`, `/api/assets/uploads/*` | Медиатека, приватное чтение с Range и загрузка. |
| `/api/connections`, `/api/voices` | Наличие и изменение ключей, выбор доступных голосов. |

Маршруты `generate-*` вложены в `/api/projects/:id`. Они проверяют весь состав серии до добавления jobs: ревизию, предыдущие утверждения, модели, принадлежность файлов, лимиты, речь и бюджет. `batchId` обеспечивает идемпотентность повторного подтверждения того же диалога. Повтор с уже сохранённым batchId не должен создавать вторую платную серию.

### Конечный автомат задачи

```text
queued -> dispatching -> pending -> saving -> done
                   \-> saving -> done
                   \-> done                  (текст / синхронный ответ)
queued -> cancelled                           (до отправки)
dispatching -> failed | unknown
pending -> pending | failed | saving | done
saving -> saving | done                       (повтор сохранения результата)
```

Перед внешним вызовом сервер атомарно переводит queued в dispatching. Он повторно проверяет основу, выбранные источники sync и пригодность текста речи. Если основа изменилась до отправки, задача отменяется без вызова модели.

Синхронный запрос может занять до 180 секунд. Асинхронный ответ сохраняет `requestId`/`pollingUrl`, после чего очередной запрос клиента опрашивает существующую задачу. Статус pending не означает создание нового запроса генерации. Скачивание результата ограничено по времени и размеру; разрешённые адреса и перенаправления проверяются провайдерским адаптером.

Receipt, usage и известный URL результата сохраняются до создания окончательного варианта. Файл результата обычно имеет ID задачи. Повторное сохранение и добавление варианта проверяют существующую связь с `jobId`.

При неопределённом сетевом исходе нельзя обещать, что платный запрос не дошёл. Задача становится unknown и автоматически заново не отправляется. Dispatching без завершения более 15 минут также может стать unknown. Определённая локальная ошибка до отправки получает нулевой расход; HTTP-ошибка после отправки сама по себе нулевой расход не доказывает.

Отдельные recovery-команды проверяют сохранённый запрос sync либо уже принадлежащий владельцу файл пробы голоса. Они не возвращают платную задачу в queued.

### Почему нужен открытый браузер

Таймер `app/studio.tsx` примерно раз в 5 секунд выбирает сначала pending/dispatching/saving, затем queued, и отправляет POST задачи. В одном окне одновременно выполняется один такой запрос. Таймер работает только для открытого проекта. На сервере нет cron, worker-процесса обхода всех проектов или облачной очереди, которая продолжала бы этот цикл самостоятельно.

После закрытия вкладки внешний провайдер может закончить уже принятую работу, но её следующий опрос и локальное сохранение возобновятся после открытия проекта. Перезапуск VPS не должен сбрасывать receipt или превращать unknown в новую попытку. CAS защищает повторную отправку queued при нескольких клиентах; это не полная распределённая система блокировок для всех стадий polling и хранения.

## 9. Согласованность планов, речи и референсов

Карточки этапов 5/6/7 связываются с планом через `sourceShot`: источник сценария, название, канонический ключ и версию. `plan-sync.ts` обновляет связи только при допустимом сопоставлении. Неоднозначные планы не должны объединяться по позиции массива.

Дубликаты и удалённые из сценария карточки получают `planArchive`; файлы, варианты и jobs остаются. Архив исключается из активных генераций, зависимостей и монтажа. `planDraft` отличает доказанный системный черновик от ручной правки; только такой черновик может автоматически получить новую версию описания.

`speechType` принимает `voiceover`, `character`, `none`; `speaker` хранит одного говорящего. Старый непустой dialogue без типа трактуется как voiceover. Очистка `spokenText` применяется к исходному тексту перед отправкой TTS, но не изменяет готовую запись.

При построении звука и инструкций используется фактическая актуальная аудиокарточка, затем подходящие данные раскадровки/сценария. Нельзя безусловно затирать ручной текст новым parseShots. Для character обязательны имя и произносимая реплика; для none текст должен быть пустым. Правило речи добавляется сервером, включая ручные видеопромпты.

Утверждённые герои содержат snapshot описания в варианте и asset изображения. Черновик карточки не заменяет этот snapshot. Изображения героев автоматически объединяются с дополнительными референсами, лимиты проверяются до создания серии. `storyboard-image-prompt.ts` собирает компактную основу одного плана и общий полный запрос для UI, single и batch; он не должен сериализовать всю историю вариантов проекта.

## 10. Монтаж и sync в браузере

`editPlan` строит монтаж из участвующих утверждённых кадров или видео и соответствующей озвучки. Для аниматика используется выбранное актуальное аудио; для финала — утверждённое, с проверкой нового выбора. Файлы загружаются через приватный asset API.

В режиме plans `fitPlanToSpeech` учитывает измеренную длительность речи после trim, продлевает визуальный план и сдвигает все последующие начала. Расписание выравнивается по 24 кадрам/с. Только избыточное округление может быть компенсировано кадром, который не нужен полной речи; реальное превышение 60 секунд остаётся ошибкой. Финальный диапазон — 1080–1440 кадров.

В браузере сначала может использоваться HTMLAudio metadata для предварительной оценки. Во время реальной сборки FFmpeg проверяет исходные файлы через ffprobe. Для видео дополнительно проверяется доступная длина после trim; отсутствующие секунды исходного ролика не создаются молча.

`renderFilm` создаёт видео 1920×1080 или 1080×1920 с прямыми склейками. Звук исходных роликов удаляется, отдельные дорожки обрезаются/сдвигаются по монтажному плану и смешиваются. Движок работает в браузерном Worker, с одним потоком кодирования. Отмена прекращает этот экземпляр FFmpeg.

Подготовка sync также выполняется в браузере. Для видео создаются нормализованный участок до 1280×720/24fps и отдельная аудиозапись; для image-режима — изображение, указатель лица и подготовленная речь. Сервер повторно проверяет утверждённые IDs, затем отправляет приватные файлы провайдеру multipart-запросом.

`scripts/prepare-media.mjs` воспроизводит статические части движка из npm-зависимостей. `wasm.ts` читает `/ffmpeg/core.json`, загружает части и собирает Blob; пути Worker/JS должны быть доступны с того же origin. Публикация одного Next.js server bundle без статики FFmpeg сломает монтаж.

## 11. Учёт денег

В проекте суммы сериализуются как строки целых USD ticks, 10^10 ticks на доллар. Расчёты используют BigInt, чтобы не накапливать ошибку float.

`estimate` — оценка одной попытки; `actual` — подтверждённая сумма или null. `actualSource` фиксирует происхождение факта. `usage` и квитанция API хранятся отдельно. Отсутствие суммы не равно нулю.

Лимит проверяется перед постановкой серии: подтверждённые расходы + зарезервированные оценки + новые оценки. Неизвестные расходы препятствуют уверенному расчёту лимита. Оценка по тарифу, включая расчёт GPT Image по токенам без известной скидки за кэш, не записывается как подтверждённый actual.

Удаление варианта или карточки не удаляет job и не возвращает деньги. Повторный запуск нового batch — новая потенциально платная работа. Идемпотентность действует для повтора того же сохранённого batchId, а не для любых внешне одинаковых промптов.

## 12. Эксплуатационные границы и проверка изменений

Эта архитектура предполагает один Node-процесс приложения и один постоянный локальный DATA_DIR. Несколько контейнеров с отдельными дисками не образуют общую студию. Несколько процессов с общей SQLite/файлами не поддерживаются: SQLite WAL не заменяет межпроцессные блокировки публикации объектов и multipart-сессий. PM2 cluster и несколько app replicas нельзя включать без доработки адаптера.

Дисковое хранилище, SQLite и секреты нужно сохранять согласованно. SQL backup без приватных snapshots и assets не содержит полного фильма. Смена owner требует учесть область snapshot и AAD ключей. Автоматическая миграция пользовательских данных в состав приложения не подразумевается.

Reverse proxy должен поддерживать Range, загрузку частей и длительные запросы провайдеров. При ограничениях тела и таймаутов важно различать multipart-загрузку пользователя, скачивание результата и ожидание синхронного API. Сброс соединения не доказывает отсутствие платного вызова.

При изменениях адаптера полезны следующие проверки:

1. Два конкурентных UPDATE одной ревизии: один успех, один 409; чужой owner не получает проект или asset.
2. Inline и большой snapshot: точный round-trip, проверка hash/size/revision, ошибка отсутствующего файла без замены данных.
3. Range: полный GET, начало/конец/суффикс, размер тела, Content-Range и перемотка media.
4. Multipart: повтор части, неверный etag, потерянный ответ complete, повтор complete и abort после завершения без удаления результата.
5. Повтор batchId и конкурентный запуск queued не создают новый платный запрос; unknown не пересылается.
6. Смена утверждённой основы отменяет ещё не отправленный job, но сохраняет историю; удаление/восстановление не утверждает автоматически.
7. Изменение текста/вида речи до TTS, ручная аудиоверсия, VO без артикуляции, запрет sync для VO/none.
8. Реальная браузерная сборка с полными репликами, дробными кадрами, перемещением планов, нехваткой исходного видео и повторным просмотром аниматика.

Тесты в `tests/` проверяют предметные сценарии, провайдерские контракты и инфраструктурные операции. При изменении среды выполнения отдельно проверяются авторизация и HTTP/storage-интеграция: подмена провайдера в модульном тесте не проверяет запуск настоящего сервера. Работоспособность установки, реальные платные модели и восстановление из резервной копии проверяются отдельно от модульных тестов.
