# HTTP 500 при генерации изображений

В журнале Cloudflare обнаружены два POST `/api/projects/:id/jobs/:jobId`
с outcome `exceededMemory`. Платформа прекращает выполнение Worker и возвращает
HTML вместо JSON; обычный обработчик API не может перехватить такую остановку.
Идентификаторы маршрутов в логах скрыты, поэтому точную попытку нужно сверять
с журналом фильма, а не считать любую генерацию ошибочной.

Устранена избыточная аллокация при декодировании base64: `Uint8Array.from(atob(...), ...)`
перебирает строку через промежуточный массив. Общий декодер заранее выделяет
бинарный буфер и заполняет его блоками не более 24 КиБ. Он используется для
референсов и результатов GPT Image, загрузок ZenCreator, inline-видео Google
и проб голосов ElevenLabs. Форматы, качество, количество параллельных запросов,
квитанции и учёт стоимости не изменены.

Проверка `node tests/media-memory.mjs`: границы блоков, padding, неполный padding,
ASCII-пробелы, неверные данные и три параллельных GPT Image edits в workerd;
каждый получает два референса по 2 МиБ и возвращает изображение 6 МиБ.
Все HTTP-ответы подменены локально, платных обращений нет.

Обновление кода не восстанавливает потерянный ответ синхронной генерации.
Если результат уже сохранён, он остаётся в карточке. При неизвестном исходе
без квитанции/ссылки нужно сверить результат и списание в кабинете провайдера.
Приложение не отправляет генерацию повторно автоматически. У строк журнала
есть `data-job-id`, позволяющий сопоставить конкретную попытку с HTTP-маршрутом.

Если файл уже был записан под ID попытки, кнопка «Восстановить сохранённую
картинку» в журнале проверяет владельца, точный проект, MIME и размер объекта
и восстанавливает вариант с первоначальным промптом, зависимостями и ролью
ключевого кадра. Текущий выбор сохраняется; старый материал не получает
автоматическое утверждение для новой основы. Повторное восстановление не
создаёт дубль. Ключ модели, референсы и API провайдера не используются.
При отсутствии файла статус и расходы не изменяются. Для обычного завершения
и восстановления применяется одна функция сохранения результата.

После ответа провайдера массивы base64-референсов очищаются до записи снимка
проекта; после записи файла освобождается бинарный результат до заключительной
CAS-записи. Тест `node tests/image-file-recovery.mjs` проверяет HTTP-обработчик,
изоляцию владельца/проекта, неизменность квитанции/расходов/основы, повторное
нажатие и отказ без файла или при несоответствии MIME/размера.

## 5 октября 2026: большой снимок проекта и параллельная обработка

Повторные `exceededMemory` подтвердили второй источник нагрузки: снимок текущего
фильма превышает 18 МБ, а несколько обработчиков одновременно держали его копии,
base64-референсы и multipart-тела. Одного блочного декодирования недостаточно.

GPT Image теперь получает исходные Blob-файлы напрямую, после проверки владельца,
проекта, MIME, размера каждого файла и суммарного лимита. Промпт, разрешение,
`quality: high` и байты референсов сохранены. Проверка HTTP-запроса больше не создаёт
вторую multipart-копию. Предыдущий снимок освобождается перед загрузкой нового,
а после проверки референсов не удерживается во время ожидания провайдера.

На Sites один Worker isolate допускает одну тяжёлую медиаоперацию одновременно.
Конкурирующий вызов получает JSON 503 `MEDIA_WORKER_BUSY` и Retry-After: 5 **до**
загрузки проекта, изменения статуса, получения ключа или обращения к провайдеру.
Клиент оставляет тот же ID в очереди для следующего тика. Это не повтор отправленного
платного запроса; неизвестные исходы по-прежнему не отправляются автоматически.
Ограничитель общий для HTTP-обработчика и фонового медиаисполнителя, освобождается
при успехе и исключении. Он действует внутри isolate, а межпроцессную идемпотентность
по-прежнему обеспечивает CAS. Отдельный Node-сервер сохраняет свою параллельность.

Регрессия `tests/hosted-media-memory.mjs` использует реальный workerd/R2: снимок
более 18 МБ, два исходных референса по 3 МБ, результат 6 МБ, три одновременных
POST. Проверяются один вызов провайдера, два отказа до отправки с сохранением
очереди, квитанция, архив проекта, результат, освобождение слота и идемпотентность.
Ответ провайдера подменён; платных обращений в тестах нет.

### Подготовка видеопланов из аниматика

`POST /video-preparation` также входит в общий слот до чтения снимка фильма.
Вместо `structuredClone` всего проекта создаётся отдельная оболочка проекта и
карточек видеопланов/реплик, которые может обновить согласование планов. История,
задания, варианты и сохранённые аниматики не копируются и не изменяются. Владение
каждым уникальным исходным файлом проверяется до сохранения, запись сохраняет CAS.
Отказ в проверке не меняет исходный снимок.

Кнопка подготовки оформлена основной кнопкой, показывает «Подготавливаем
видеопланы…» и защищена от повторного нажатия до завершения запроса. Подготовка
переносит исходные кадры и длительности, но не запускает генерацию и не расходует
баланс моделей. При занятом сервере показывает понятное сообщение без повтора.

`tests/video-preparation-memory.mjs` проверяет в workerd проект более 18 МБ,
16 пар начальных/конечных кадров, сохранение исходных длительностей и истории,
отказ конкурирующему вызову до загрузки данных и повторную подготовку без дублей.
Отдельный Node-сервер использует ту же экономную копию и защиту кнопки; общий
лимит медиаопераций Worker на него не переносится.

### Обновления очереди и списка файлов (6 октября)

Список файлов использует сохранённый вместе с ревизией компактный assetIds в D1-конверте. Он по-прежнему пересекается с файлами владельца; старые ссылки и импортированные материалы сохранены. Старый конверт без индекса читает полный снимок только через свободный слот. Начальная загрузка списка следует за загрузкой проекта.

Обычный jobs POST и восстановление результата не запускают дополнительный waitUntil worker: следующие тики открытой вкладки продолжают уже созданные задания. Фоновый tick занимает слот до загрузки selector snapshot, освобождает этот снимок до I/O, запускает один небольшой async submit. Pending/saving остаются foreground, поскольку скачивание не обязано укладываться в 30 секунд. Локальные flight и слот фонового события истекают через 35 секунд; durable dispatching, квитанции и расходы не сбрасываются.

`tests/hosted-asset-list-memory.mjs` проверяет реальный Workers/D1/R2: список проекта >18 МБ доступен даже при занятом медиа-слоте и без чтения большого снимка; чужие файлы не выдаются, старый формат откладывается до освобождения памяти.
